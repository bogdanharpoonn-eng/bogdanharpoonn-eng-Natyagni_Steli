# ПРОМТ ДЛЯ CURSOR — MVP «Замір натяжних стель» (PWA)

> Скопіюй усе нижче в Cursor (Agent mode). Рекомендовано також зберегти розділи 2–9 у файл `.cursor/rules/project.mdc`, щоб правила діяли в кожному запиті.

## 0. Роль і режим роботи

Ти — senior full-stack розробник і спеціаліст з обчислювальної геометрії. Ми будуємо MVP B2B-продукту для замірників натяжних стель в Україні. Продукт продаватиметься виробникам стель за ліцензіями.

**Правила роботи:**
1. Працюй **строго поетапно** (розділ 10). Після кожного етапу — зупинись, коротко опиши, що зроблено, як перевірити, і **чекай мого підтвердження**.
2. Перед початком етапу — опиши план файлів і рішень (5–10 рядків).
3. Не вигадуй вимог. Якщо щось неоднозначне — запитай, а не припускай мовчки. Усі припущення фіксуй у `docs/DECISIONS.md`.
4. Не додавай функцій поза поточним етапом.

## 1. Продукт і користувач

- **Користувач:** замірник натяжних стель. Працює на об'єкті, часто однією рукою, з рулеткою або лазерним далекоміром, у поганому освітленні, іноді без інтернету.
- **Задача:** швидко внести виміри приміщення (сторони A-B, B-C, …, діагоналі) → отримати **точне креслення стелі**, площу, периметр, кути → надіслати клієнту/виробнику.
- **Головна цінність:** **жодної помилки заміру не доходить до виробництва** (контроль похибки по діагоналях).
- **Принцип UX:** простіше за конкурентів. Кожна функція має бути потрібна замірнику на об'єкті — інакше її немає в MVP.

---

## 2. Технічний стек (обов'язковий)

- **React 18 + TypeScript (strict) + Vite**
- **PWA:** `vite-plugin-pwa`, повна офлайн-робота, встановлення на головний екран iOS/Android
- **Стан:** Zustand
- **Локальне сховище:** IndexedDB через Dexie (автозбереження кожної зміни)
- **Креслення:** SVG (власний компонент, без canvas-бібліотек)
- **Валідація:** Zod
- **Стилі:** Tailwind CSS
- **PDF:** jsPDF + svg2pdf.js
- **Тести:** Vitest (геометрія — обов'язково), Playwright (e2e основного сценарію)
- **Якість:** ESLint + Prettier, заборонено `any`, без попереджень у збірці

**Архітектура:** геометричне ядро — окремий чистий модуль `src/core/geometry/` без залежностей від React/UI, повністю покритий тестами. Шар даних — через репозиторій-інтерфейс, щоб пізніше замінити IndexedDB на синхронізацію з сервером без переписування UI.

## 3. Модель даних

```ts
Order        { id, createdAt, updatedAt, client: { name, phone, address }, note, rooms: Room[], status: 'draft' | 'done' | 'sent' }
Room         { id, name, height?: mm, vertices: Vertex[], sides: Side[], diagonals: Diagonal[], fixtures: Fixture[], note }
Vertex       { id, label /* A, B, C… */, cornerType: 'internal' | 'external' /* внутрішній/зовнішній кут */ }
Side         { from: label, to: label, length: mm }
Diagonal     { from: label, to: label, length: mm, isControl: boolean }
Fixture      { id, type: 'light' | 'pipe' | 'chandelier', x: mm, y: mm }   // етап 5, модель закласти зараз
```

- **Усі довжини зберігати в міліметрах (integer).** Введення та відображення — у **сантиметрах з 1 знаком після коми** (налаштування).
- Схема даних версіонується (`schemaVersion`), міграції Dexie — з першого дня.

## 4. Геометричне ядро (найважливіше)

### 4.1 Вхід
- Багатокутник з *n* вершинами (n ≥ 3, MVP до 20), вершини позначаються A, B, C… **за годинниковою стрілкою**.
- *n* сторін + діагоналі.
- **Мінімум для побудови:** n − 3 діагоналі, які утворюють тріангуляцію. Решта діагоналей — **контрольні**.
- Для кожної вершини — тип кута (внутрішній/зовнішній), за замовчуванням зовнішній (опуклий).

### 4.2 Алгоритм
1. Перевірити, що задані діагоналі утворюють коректну тріангуляцію (без перетинів, покривають багатокутник). Якщо ні — вказати, **яких саме діагоналей бракує** (запропонувати конкретні, напр. «додайте A-C»).
2. Перевірити нерівність трикутника для кожного трикутника. Порушення → помилка з назвою трикутника та сторін.
3. Побудова: перша сторона на осі X, далі послідовне розміщення вершин через перетин двох кіл (трилатерація). Неоднозначність дзеркального розміщення вирішувати за орієнтацією обходу (за годинниковою) та типом кута.
4. Якщо є контрольні діагоналі — **урівноваження методом найменших квадратів** (Gauss-Newton / Levenberg-Marquardt) по всіх вимірах.
5. Перевірити, що результуючий багатокутник **не самоперетинається**.

### 4.3 Вихід
- Координати вершин (мм)
- Площа (м², 2 знаки), периметр (м, 2 знаки)
- Внутрішні кути кожної вершини (°, 1 знак)
- Кількість внутрішніх/зовнішніх кутів
- **Похибка:** для кожного виміру — різниця «введено vs розраховано»; максимальна похибка; статус:
  - ✅ ≤ допуску (за замовчуванням **10 мм**, налаштовується)
  - ⚠️ допуск < похибка ≤ 2× допуску — «перевірте виміри»
  - ❌ > 2× допуску — «переміряйте: найімовірніше помилка у <сторона/діагональ>» (вказати вимір з найбільшим залишком)

### 4.4 Тести (обов'язкові фікстури)
- Прямокутник 400×300 см, діагональ 500 → кути 90°, площа 12,00 м²
- Прямокутник з контрольною діагоналлю, що відрізняється на 3 мм → ✅; на 25 мм → ❌ з правильною вказівкою виміру
- Трапеція, паралелограм (сторони однакові з прямокутником — інша форма через діагональ)
- Г-подібне приміщення (6 кутів, 1 внутрішній)
- П-подібне (8 кутів, 2 внутрішні)
- Недостатньо діагоналей → зрозуміла помилка з пропозицією
- Порушення нерівності трикутника
- Самоперетин

## 5. UX і інтерфейс

- **Мова інтерфейсу: українська.** Усі тексти — у `src/i18n/uk.ts` (підготовка до інших мов).
- **Mobile-first**, мінімальна ширина 360 px, кнопки ≥ 48 px, великі поля вводу, цифрова клавіатура (`inputmode="decimal"`).
- **Режим «на об'єкті»:** високий контраст, підтримка темної теми, читається на сонці.
- **Послідовне введення:** після A-B фокус автоматично переходить на B-C і т.д.; після сторін — запропонувати потрібні діагоналі.
- **Живе креслення:** ескіз оновлюється після кожного введеного значення; проблемні виміри підсвічуються червоним на кресленні.
- **Креслення:** у масштабі, підписи вершин і довжин, діагоналі пунктиром, zoom/pan жестами, кнопка «вписати в екран».
- **Швидкі шаблони:** прямокутник (4 кути), Г-подібна (6), П-подібна (8), довільна (N).
- **Нуль втрати даних:** автозбереження кожної зміни, робота після закриття/перезапуску.
- Будь-яка дія — максимум **3 тапи** від головного екрана.

### Екрани MVP
1. **Замовлення** — список (пошук за ім'ям/телефоном/адресою), кнопка «+ Новий замір»
2. **Замовлення** — дані клієнта + список приміщень (кожне з мініатюрою креслення, площею, статусом похибки)
3. **Приміщення** — введення вимірів + живе креслення + результати
4. **Налаштування** — одиниці, допуск похибки, тема, дані замірника/компанії (для PDF)

---

## 6. Експорт і відправка

- **PDF замовлення:** шапка (компанія, замірник, дата, клієнт), для кожного приміщення — креслення + таблиця вимірів + площа/периметр/кути + статус похибки, підсумок по замовленню.
- **PNG креслення** кожного приміщення.
- **Відправка** через Web Share API (Telegram, Viber, пошта) — одна кнопка «Надіслати».
- Експорт/імпорт замовлення у **JSON** (резервна копія + майбутня передача на виробництво).

---

## 7. Чого НЕ робити в MVP

Без бекенду, авторизації, ліцензій, оплат, розкрою полотна, 3D, кошторисів/прайсів, CRM, Bluetooth-рулеток, криволінійних стін, багаторівневих стель. **Але** модель даних і архітектура не повинні блокувати ці функції в майбутньому — фіксуй точки розширення в `docs/ROADMAP.md`.

---

## 8. Помилки конкурентів, яких уникаємо (гіпотези, перевіряються на пілоті)

- Перевантажений інтерфейс → тільки функції для заміру
- Відсутній контроль похибки → обов'язкова перевірка по контрольних діагоналях
- Втрата даних без інтернету → offline-first
- Складне введення довільних форм → покрокове введення + шаблони + підказки діагоналей
- Незрозумілі помилки → кожна помилка каже, **що саме** і **як виправити**

---

## 9. Критерії приймання MVP (Definition of Done)

- [ ] Усі тести геометрії з п. 4.4 проходять
- [ ] Прямокутна кімната вводиться і креслиться **≤ 60 секунд**
- [ ] Г-подібна кімната — **≤ 2 хвилин**
- [ ] Додаток повністю працює в режимі «в літаку» після першого завантаження
- [ ] Встановлюється на головний екран iPhone (Safari) і Android (Chrome)
- [ ] PDF відкривається коректно, креслення векторне
- [ ] Lighthouse PWA ✅, Performance ≥ 90 на мобільному
- [ ] Перезапуск додатку посеред введення не втрачає жодного значення
- [ ] Немає `any`, ESLint/TS без помилок, e2e основного сценарію проходить

## 10. Етапи (після кожного — стоп і підтвердження)

1. **Каркас проєкту:** Vite + TS + Tailwind + PWA + ESLint + Vitest, структура папок, `docs/DECISIONS.md`, `docs/ROADMAP.md`
2. **Геометричне ядро + усі тести з п. 4.4** (без UI)
3. **Модель даних + Dexie + репозиторій + автозбереження**
4. **Екран «Приміщення»:** введення + живе креслення + результати + похибка
5. **Екрани «Замовлення» і «Список замовлень», шаблони кімнат**
6. **PDF/PNG/JSON експорт + Web Share**
7. **Налаштування, темна тема, офлайн-перевірка, Lighthouse, e2e-тести**
8. **Фінальна перевірка за п. 9** — звіт: що виконано, що ні, відомі обмеження
